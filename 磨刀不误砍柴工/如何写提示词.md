# 方法论

> 好比去医院看病
> 
> 提示词的本质不是命令
> 
> 而是沟通

## 1. 找对科室

```
假设你是
```

指定一个具体的角色身份——某个行业的名人，或一个具有特定经验和经历的人。

角色不是越厉害越好，而是越具体越好。

|    弱     |                   强                   |
| :------: | :-----------------------------------: |
| 假设你是李彦宏  | 假设你是有15年搜索引擎产品经验的产品总监，熟悉从0到1的技术产品立项流程 |
| 假设你是设计师  |   假设你是专注移动端用户体验、做过多款千万级DAU产品的交互设计师    |
| 假设你是程序员  |        假设你是有10年后端开发经验的Java工程师         |
| 假设你是产品经理 |       假设你是负责过百万用户产品从0到1上线的产品经理        |

名字是标签，经验描述的作用是缩小回答范围。

---

## 2. 说明病情

### 2.1. 现状

描述自己的各方面情况，越具体越好。

```
1. 我是谁
2. 我目前在做什么
3. 做了xxx
4. 遇到了xxx问题
```

### 2.2. 期望

预期达到的目标和效果。

```
我的期望如下/满足以下条件视为完成：
1. 
2. 
3. 
...
```

### 2.3. 家底

分两部分填写，性质不同，不要混在一起

#### 2.3.1. 资源

已有的资源、文件、代码、调研结果、可用工具和环境

```
我有以下资源：
1. 
2. 
3. 
...
请优先基于已有资源分析，不要忽略资源中的内容。
```

#### 2.3.2. 限制

**必须满足，不能使用**、预算上限、版本要求等限制

```
我有以下限制：
1. 必须满足
2. 不能使用
...
```


> 「约束条件」这个块是整个模板里最容易被忽略、但价值最高的部分——它能大幅减少 AI 给出"方向正确但无法实操"的建议。

---

## 3. 请求开药

直接说明：

```
请帮我
```

说清楚要 AI 做的具体事情。

---

## 4. 治疗方式

### 4.1. 参考

> 参考往往比描述更有效。

如果有参考资料，直接给出

```
【参考】参考xxx（文件或案例），以其思考方式、表达格式、语言风格、语气为准。若与本文的规则冲突，以规则为准。
```

### 4.2. 思考

减小AI幻觉

```
回答问题时需避免过分的夸赞。请记住，你的回答不一定是对的，我的判断也不一定是对的。对待所有问题都要反复推敲，优先保证准确性，必要时你可以主动向我索要补充信息或证据。
```

### 4.3. 输出

> 有参考先根据参考的xxx输出

#### 4.3.1. 格式

例如

|               格式                |
| :-----------------------------: |
|          分段阐述，按数字序号排列           |
|         无需分段，以文字段落的形式表达         |
|           用 xxx 格式回答我           |
|           用表格的形式列出回答            |
|       先详细解释原理，再用注释清晰的代码回答       |
| 涉及的 Markdown 文字或代码不要出现 emoji 表情 |

#### 4.3.2. 风格

 ```
结构化输出，条理清晰，符合金字塔原理——自上而下，结论先行，层层支撑。语言xxx。
 ```

#### 4.3.3. 结构

```
正式回答前，按以下顺序输出前置内容，再进入正文：
1. 对我输入内容的理解与概括
2. 本次回答将输出的内容概要
3. 存在的疑问或需要我补充的信息
```
