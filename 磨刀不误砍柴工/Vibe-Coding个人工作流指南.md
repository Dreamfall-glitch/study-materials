> 从零开启项目

---

# 一、梦开始的地方

一切从新建目录开始。

通过终端命令
```bash
mkdir res output proj mylog
touch requirement.md task.md 
```

```PowerShell
mkdir res, output, proj, mylog
New-Item requirement.md, task.md
```

快速执行

第一件事是 `git init`——不需要 GitHub，本地仓库就够。每次 AI 输出一版结果就 `git commit -m "message"` 一次，message 一句话即可。

项目目录结构如下：

```
project/
├── .git/
├── requirement.md
├── task.md
├── res/
│   ├── 01-xxx.md
│   ├── 02-xxx.md
│   ├── 03-xxx.md
|   └── ...
├── mylog/
|   ├── 01-xxx.md
|   └── 02-xxx.md
└─- output/
|   ├── 01-思路梳理-v1.md
|   ├── 02-方案评估-v1.md
|   ├── 02-方案评估-v2.md
|   ├── 03-最终方案-v1.md
|   └── ...
└─- proj/
```


文件尽量用「阶段序号 + 名称 + 版本号」命名。前缀数字表示项目推进阶段，后缀版本号表示该阶段的迭代次数，名称要求简洁明了、突出核心。

> **实践经验**：后续可能需要添加`data/` `photo/` `report/`等文件夹用于数据记录和报告编写

# 二、写 requirement.md：总要求

这是整个项目的地基。把要求说清楚，一般是官方内容。不需要很长，但要具体清晰。

---

# 三、写 task.md：用模板构造提示词

参考 [如何写提示词](如何写提示词.md)

按照以下模板结构写每一次任务的核心提示词：

```
【角色】假设你是

【现状】
1. 我是谁
2. 我目前在做什么，核心要求已写入 @requirement.md 中，需全程围绕此目标严格执行并遵守约束
3. 做了xxx
4. 遇到了xxx问题

【目标】满足以下条件视为完成：
1. 
2. 
3. 

【资源】
1. @res/ 目录下的所有文件均为参考，思考过程中请优先基于已有资源分析，不要忽略其中的内容
2. @mylog/ 目录为项目日志，每条日志将记录每一轮：对话的补充与回答、项目执行过程与结果（含正确/错误）、迭代的提示词版本
3. @proj/ 目录为项目目录，项目过程中可随时查看但未经允许不得私自更改

【限制】
1. 必须满足
2. 不能使用
（以上条目若留空，视为无额外限制）

【请求】请帮我

【参考】参考xxx（文件或案例），以其思考方式、表达格式、语言风格、语气为准。若与本文的规则冲突，以规则为准。

【思考】回答问题时需避免过分的夸赞。请记住，你的回答不一定是对的，我的判断也不一定是对的。对待所有问题都要反复推敲，优先保证准确性，必要时你可以主动向我索要补充信息或证据。

【输出格式】
1. 默认输出 Markdown 格式文件
2. 默认存入 output/ 目录下
3. 文件按「阶段序号 + 名称 + 版本号」命名，如 01-思路梳理-v1.md。前缀数字表示项目推进阶段，后缀版本号表示该阶段的迭代次数，名称需简洁明了、突出核心

【输出风格】结构化输出，条理清晰，符合金字塔原理——自上而下，结论先行，层层支撑。语言xxx。

【输出结构】正式回答前，按以下顺序输出前置内容，再进入正文：
1. 对我输入内容的理解与概括
2. 本次回答将输出的内容概要
3. 存在的疑问或需要我补充的信息

【自检】输出前检查：
1. 是否满足全部限制条件 
2. 是否遵循了思考规范及输出要求
3. 是否遗漏重要风险
4. 是否存在明显更简单的方案
如有未通过项，在正文末尾标注。
```

> **亲测经验**：最好自己套用模版自己写，不要交给AI写，在此模版基础上可以无需繁杂吩咐

---

# 四、整理参考资料，放入 res/

用搜索引擎检索相关资料、图片或视频，整理成文字，分类存入 `res/` 目录。

> 利用检索增强生成（RAG）使结果更准确

---

# 五、AI 输出写入 output/

把 `requirement.md`、`task.md` 和 `res/` 里的参考资料一起喂给 AI。输出结果按命名约定存入 `output/`，然后立刻 commit 一次。

---

# 六、岁月史书 mylog/

回答AI列出的确认问题并根据 AI 的输出内容进行自己的设计和判断，补充遗漏的资料。

无疑问就正常执行任务，在 `proj/` 里开展工作空间，遇到问题先看看网页端大模型能否解决。

`mylog/` 目录为项目日志，每条日志要记录每一轮：**对话的补充与回答、项目执行过程与结果（含正确/错误）、迭代的提示词版本**。命名方式简洁并规整化。

> 建立评估体系来量化衡量提示词修改的效果，然后逐一诊断失败模式并针对性解决，而非盲目地反复试错。

---

# 七、整体流程一览

```
新建项目目录 + git init
        ↓
写 requirement.md（定义核心目标）
        ↓
写 task.md（用模板构造提示词）
        ↓
整理参考资料 → res/01-xxx.md
        ↓
AI 结合资料输出 → output/01-xxx-v1.md + git commit
        ↓
审阅输出，回答确认问题，补充遗漏资料 → mylog/01-xxx.md
        ↓
在 proj/ 开展项目工作
		↓
执行日志 → mylog/01-xxx.md
		↓
根据项目执行过程与结果，提出新一轮提示词
        ↓
	   ...
```

# 八、经验向

## 我们更需要什么

1. 过硬的基础知识

2. RAG（检索增强生成 Retrieval-Augmented Generation）与交互性

3. 对信息的整合能力和整理调用能力，输入信息要多考虑AI可读性

## 细节技巧

1. AI 服务于人而不是人服务于 AI

2. 提示词在完备的前提下，简单，简单，再简单

3. 关于显示格式：HTML给人看，Markdown给ai看

4. AI目前还是只擅长做体力活，不擅长或难以做复杂的脑力工作，最好的打开方式是自己有一个大致的脉络和检验方法，然后再去进行

5. `/compact`是个好东西
